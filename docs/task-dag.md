# Task DAG and card choreography

Task detail modals reserve a large graph viewport above the existing information, plans, approval controls, evidence, activity and conversation. Task records and authorization are unchanged.

The browser uses the already-authorized task projection. Solid arrows mean recorded prerequisite → dependent. Feature membership comes from explicit feature mappings or legacy tasks explicitly typed Feature. Purple dashed links describe recorded date order within a feature (completedAt, then finalApproval.at for ready tasks, then createdAt), or undirected shared membership when dates are absent/equal. Dates never create dependency gates, completion claims or causal ordering. Missing records are reported without inventing nodes or content.

An iterative strongly connected component pass identifies dependency cycles across the related component before layout. Cyclic nodes and their internal dependency edges are red. Ranking uses the dependency condensation graph; history does not affect ranks. The UI calls cyclic data a dependency graph instead of claiming it is a DAG.

The initial view shows 18 tasks nearest the selection. “Show more” increases this by 18 to a maximum of 72. Up to 180 edges are drawn, prioritizing the selected task and cycles. The accessible relationship list retains the additional visible-node edges. A search over remaining related tasks can recenter the graph when the size limit is reached. Pan, zoom, Fit all, selectable cards, a task selector and textual records are available.

## Three.js rendering

`task-dag-three.mjs` uses Three.js WebGLRenderer with one perspective camera for curved connections and flat arrowheads. Cards use native DOM throughout their entrance and settled state. Actual visible board-card rectangles are captured before modal mount to locate the flight origins; their content is not cloned into the graph. Three.js is pinned in package-lock and bundled into a same-origin module by esbuild. No CDN or runtime service is required.

The selected card starts first; related cards follow with a short bounded stagger. Off-screen cards start below the viewport. Cards keep one title/stage layout and the same DOM nodes through landing. Screen positions, dimensions, native font sizes and shadows animate without CSS perspective, rotation or scale transforms. Their graph aspect ratio is maintained even when the originating board card is shorter. Positions, sizes and typography are aligned to device pixels. Cards are 260 × 160 px. Titles use a 24 px base size and stages 17 px; repeated sample/ID metadata is omitted from graph cards. Fictional/read-only notices remain on the surrounding demo. Text growth is capped at 125% when zooming in.

Task opening fits the entire visible graph. Fit all and the zero key restore this overview. Arrowheads are anchored at their apex on the curve, while the revealed shaft stops inside the broad base of each head. Incoming and outgoing connectors use ports allocated dynamically from their edges to avoid shared arrow tips. The same routing and trimming apply to SVG fallback markers. History links have no arrowheads. Animation stops after the reveal.

The graph retains the existing task controls below it. Switching tabs does not replay an unchanged graph. Selecting an already-visible graph task updates only selection styling, accessible selection state, and the task details below. The Three.js renderer, card objects, edge geometry, layout and camera are retained; selection does not replay the entrance animation, recenter, or reset pan/zoom. This applies to real and fictional tasks and to pointer, keyboard and select-menu navigation. Expanding the graph, changing history visibility or opening an off-graph task can create a new graph. Initial modal opening retains the original entrance animation. Close, replacement and WebGL loss remove the overlays, restore source-card visibility, cancel animation frames, detach listeners, and dispose Three.js geometries/materials/context. Resize, scrolling during a flight, tab hiding and reduced motion finish at a stable graph without repeated flight. WebGL or module-load failure leaves the SVG relationship view, controls, node navigation and text equivalents available.

Implementation reference: [Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html).

## Dynamic records

Both real tasks and demo tasks use taskDagModel; there are no fixture-specific graph coordinates or connectors. Dependencies determine ranks. Completion/readiness/creation dates determine explicitly labelled feature chronology, never prerequisites. New connected tasks are included when refreshed state arrives. Open real graphs rebuild without an entrance animation when projected titles, stages, dependencies, dates or feature mappings change; task detail forms are not replaced by that graph refresh. The 18/72-node and 180-edge display limits still apply. Unrelated tasks have their own graph when opened.

Connector routing uses smooth cubic Bezier curves shared by WebGL and SVG. Dependencies that skip columns and returning links use individually allocated lanes around the cards. Adjacent cards use a single curve; longer links pass below intervening cards when their destination is lower, and above when it is level or higher, with smooth tangent joins. Purple history links between neighbouring columns use direct curves; same-column links use compact side bows. During reveal, each head aligns to the last drawn shaft ring, with a small overlap at the base; recorded dependencies are retained even when they skip intermediate tasks.

Blue bypass connections prefer one broad cubic curve from an outward card face. The router checks the curve against card bounds before choosing it. Dense layouts use smooth S-shaped gutter transitions with horizontal tangent joins instead of tight elbow-shaped turns. Arrowhead alignment is unchanged.
