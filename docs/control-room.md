# Project ownership

The project is the assignment boundary. owner is durable; ownershipFence increments for every claim, human reassignment and reopen/complete operation. Agent task writes require the current owner identity and projectFence. The human can explicitly clear an assignment with a reason. No timeout, review stage or idle status makes an assigned project claimable.

A task execution lease lasts 15 minutes and has a separate monotonic task fence. Leases protect concurrent work and exclusive environment/component scopes. Expired leases deny writes; only the same project owner can acquire another. Heartbeats expire visually after 90 seconds and never release ownership. Pausing an agent increments its execution fence, revoking task and AI leases while retaining its projects. Project assignment and agent execution fences make old leases unusable without rewriting all tasks. Public snapshots derive each task’s owner and effective lease from these authorities; stored task owner fields are historical execution metadata.

Stages: intake → research → plan_review → build → human_review → ready. submit_plan and submit_build stop execution. Human approvals apply to the displayed task version and exact scope/plan/build revisions. The same owner receives approval and change-request notifications. Task readiness never deploys code. The human can complete a project only after every task has final approval; the owner remains recorded. Reopening resumes the same owner.

Agent reads expose available project summaries for selection and details only for their own projects. Agent writes to task rooms, task records, receipts and scoped AI jobs enforce ownership. Global AI requests may be atomically claimed by any agent; they use visible project aggregates and permitted task records. Global job ownership also persists after lease expiry; a human can reset it.

Storage uses the existing relay_control_meta and per-entity relay_control_records tables. D1 batch compare-and-set uses workspace revision and a commit token. Idempotency records commit with events and notifications. Limits remain 16 MiB per workspace, 128 KiB per record and 500 changed rows per batch. Large artifacts remain references.

Migration 0002 preserves task descriptions, evidence, approvals, messages and prior assignment records. One existing task owner becomes the project owner. Conflicting owners, or unowned real work already past intake, require human assignment. Leases are revoked, old stage offers superseded, queued old notifications cancelled and AI jobs requeued. The workspace epoch changes so pre-migration envelopes cannot execute. Former build-review tasks proceed to final human review; no separate specialist is required.

Features are Task records with type Feature. A task may reference a same-project Feature through featureId; features cannot be nested. featureGroup and layer are explicit text labels. The network derives project, feature and dependency connections from current records. Shared-component links and rationale are explicit persisted human edits. The canvas supports pan/zoom, keyboard inspection, floating information dialogs and structured chat references. See network-references.md.
